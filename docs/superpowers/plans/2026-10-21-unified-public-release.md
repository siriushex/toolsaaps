# Единый продукт: другие пользователи и сохранение интерфейса AAPS

**Статус:** дополнение к [мастер-плану](2026-10-21-unified-aaps-copilot-juggluco.md), 21 октября 2026. Основано на двух уточнениях пользователя: продукт сразу для других людей; главный интерфейс AAPS сохраняется, Copilot добавляется вкладками. Здесь перечислены проектные требования, а не реализованные функции или разрешение на публичный клинический выпуск.

## 1. Неизменяемая граница интерфейса

| Сохранить в AAPS | Добавить от Copilot |
|---|---|
| Overview, график, статус помпы/loop, болюс, treatments, профили | Прогноз с объяснением входов и качества |
| Меню, штатные диалоги подтверждения и аварийные действия | Аналитика, «Лента», оценка еды, подробности Target Manager |
| Конфигуратор, источник ГК, настройки/калибровка сенсора | ИИ-анализ: Разбор, Чат, Советы, Архив |
| Setup, objectives, защиты, режимы master/client | Дополнительные настройки Copilot и отдельное включение ИИ |

Предлагаемые внутренние routes: `copilot/prediction`, `copilot/analytics`, `copilot/ai`. Имена являются проектным предложением, не существующими API. Навигационный доступ к ним добавляется через группу Copilot/plugin registration, без замены нижних кнопок действий AAPS. Внутри страниц Copilot сохраняется его собственная вкладочная навигация.

Главный startup route не перенаправляется на Copilot. Возврат Back, configuration changes, bolus progress и срочные окна продолжают работать по правилам AAPS. Сова и motion не заменяют меню AAPS и не перекрывают индикаторы доставки. Отсутствие лицензии/сети/учётной записи ИИ не блокирует штатный интерфейс и локальную работу AAPS.

**Проверки UI:** screenshot/semantics diff штатного Overview, доступность всех старых действий, открытие каждой новой вкладки, возврат Back, deep-link без обхода protection, large font/320dp, экран во время доставки. Все клинические исходные экраны остаются функционально эквивалентны исходному AAPS при выключенных модулях Copilot.

Точки подключения в исследованной RC1:

- `app/src/main/kotlin/app/aaps/ComposeMainActivity.kt` и его `overview` callback.
- `appshell/src/commonMain/kotlin/app/aaps/appshell/navigation/AppNavGraph.kt` и `AppRoute.kt`.
- `appshell/src/commonMain/kotlin/app/aaps/appshell/navigation/ElementNavigation.kt`.
- `ui/src/commonMain/kotlin/app/aaps/ui/compose/main/MainScreen.kt`, `MainNavigationBar.kt` и существующие navigation tests.

Для Android-only Copilot нельзя добавлять безусловные Android-зависимости в `commonMain`, ломая desktop/iOS AAPS. Использовать platform slot/registration в host и явную capability на других платформах. Публичный первый scope остаётся Android; существующие общие модули не переписываются ради вкладок.

## 2. Публичный продукт не означает сразу все устройства

Матрица поддержки фиксируется до обещаний в интерфейсе/описании продукта:

`sensor model + firmware/protocol + phone/OEM + Android/API + pump model/firmware + operating mode + application version`.

Для каждой строки: владелец проверки, test fixtures, драйвер/бинарные входы и лицензия, дата аппаратного прогона, known limitations, допустимые действия, условия потери поддержки. Различать уровни **«не проверено»**, **«только отображение/импорт»**, **«проверено для заявленного режима»**. Наличие драйвера upstream не переводит строку в третий уровень автоматически.

Первые наборы выбираются по доступным тестовым устройствам и риску. Неизвестный вариант сенсора/помпы не наследует разрешение на автоматическое управление от похожего названия. Формат хранения матрицы и привязка её к exact source/build входят в release manifest/документацию продукта; сервер не может сам произвольно разрешить новое клиническое сочетание.

## 3. Назначение и условия выпуска

До определения публичного пути зафиксировать:

1. Предполагаемые пользователи и рынки, возрастные ограничения, роли пациента/наблюдателя.
2. Точное intended use: дневник, отображение, клинические рекомендации, изменение target, управление помпой. Разные наборы функций нельзя объявлять одним «информационным» продуктом, игнорируя фактическое влияние на терапию.
3. Издатель/ответственный за продукт, поддержка, процедура сообщений об ошибках и инцидентах.
4. Применимые для выбранных рынков требования к медицинскому ПО, данным и безопасности вместе с профильными специалистами. Не присваивать класс/допуск самостоятельно по этому плану.
5. Доказательства приемлемости риска и человеческого интерфейса для каждой заявленной функции. README experimental и self-build сами по себе не закрывают эту работу.

Примеры первичных ориентиров, **не вывод о применимом праве**: [FDA: device software functions](https://www.fda.gov/medical-devices/digital-health-center-excellence/device-software-functions-including-mobile-medical-applications), [European Commission: MDCG2019-11 rev.1](https://health.ec.europa.eu/latest-updates/update-mdcg-2019-11-rev1-qualification-and-classification-software-regulation-eu-2017745-and-2025-06-17_en). География публичного выпуска пока не определена.

## 4. Лицензии и воспроизводимая сборка

- Подтвердить права на объединение и распространение исходных компонентов, JNI, шрифтов, иконок, звуков и food-photo/ИИ-зависимостей.
- Согласовать лицензию принадлежащих пользователю частей Copilot; отсутствие LICENSE нельзя трактовать как разрешение всех контрибьюторов.
- Для каждого `.so`: источник, hash, ABI, версия, лицензия/разрешение, runtime callers, 16KB compatibility и процесс обновления. Существующее разрешение владельца NG на его сборку не переносится автоматически на наш продукт.
- Подготовить corresponding source, notices и точные build instructions для реально выпущенных бинарников. Не публиковать секреты или медицинские данные вместо исходников.
- Если нужная библиотека не допускает такой выпуск, исключить соответствующую поддержку из начального каталога либо получить разрешение. Не обходить подписи/лицензии и не заменять алгоритм без новой проверки.

## 5. Подпись, package и миграция чужих установок

У независимых пользователей AAPS обычно разные self-build signing keys. Публичный APK издателя не сможет просто обновить все эти установки: [Android требует допустимую signing identity для обновления](https://developer.android.com/studio/publish/app-signing).

Предлагаемый публичный путь: собственный `applicationId` и издательский release key с управлением доступом и recovery-процедурой; название/логотип не создают впечатление официального upstream AAPS. Личное in-place обновление остаётся отдельным специальным случаем при известном совпадающем ключе, а не основной схемой.

Переход: explicit export -> schema/provenance validation -> import в новый sandbox -> read-only сравнение -> согласованный handover CGM/pump -> проверка режима и фактических данных. Не запрашивать у людей private signing keys. Непереносимая BLE-сессия/Keystore identity требует отдельного supported handover/re-pairing, не хаотичного копирования файлов. До перехода нельзя иметь два активных pump controllers.

Каналы test/beta/stable имеют собственные eligibility и подписи/версии согласно выбранной стратегии. Нужны monotonic versionCode, допустимые migration tails, полная проверка подписанного APK, staged rollout и возможность прекратить предложение проблемной версии. Отзыв манифеста не удаляет установленную сборку и не является командой остановить терапию. При несовместимой миграции основной recovery является forward fix, а не старый APK/устаревшая база.

## 6. Учётные записи и медицинские данные

Оффлайн AAPS/CGM не требуют аккаунта ИИ. При включённой облачной функции разделить:

| Идентичность | Назначение |
|---|---|
| `tenant/user` | Владелец данных и права доступа |
| `device` + зарегистрированный ключ | Конкретное устройство и доказательство происхождения |
| activation/enrollment grant | Ограниченное предоставление доступа; не имя медицинской БД |
| conversation/job/report | Ресурс, всегда принадлежащий определённым user/device |
| consent revision | Разрешённые категории/цели обработки на момент операции |

Каждый upload, чтение архива, cache lookup, model context, job-result fetch и admin action проверяет владельца. Нельзя полагаться только на случайный URL, параметр deviceId или шифрование одного общего файла. Переключение пользователя на общем телефоне удаляет доступ к предыдущим credentials/caches и не наследует его контекст.

Минимальные обязательные тесты: deviceA/userA не читает/изменяет deviceB/userB; чужой job id; revoked grant во время backfill и перед отправкой модели; повтор с другим owner; worker/cache pool после ошибки; account deletion; export и admin escalation. История и чат не должны смешиваться даже при одинаковом имени устройства или одном AI provider account.

Нужны договорённости по обработке данных, уведомление пользователя, purpose-limited consent там, где применимо, экспорт/удаление, аудит доступа, encryption/key lifecycle и обоснованный retention по категориям. Исходные 365 дней не являются универсальным правовым разрешением хранить любые данные; исключения/обязательства уточняются для выбранной юрисдикции. Backup, observability и provider retention входят в ту же карту данных.

## 7. ИИ для других пользователей

Существующий личный серверный вход ChatGPT не менять. Он **не считается готовой production-авторизацией публичного multi-user сервиса** только потому, что уже работает для владельца. Новый provider access и обработка медицинских данных требуют отдельного допустимого технического/договорного контура; credentials не раздаются пользователям и не встраиваются в APK.

Варианты для отдельного решения: поддерживаемый production API с нужными договорённостями либо допустимая индивидуальная авторизация пользователя. Сохранение той же модели возможно только при её реальной доступности в выбранном контуре; не имитировать её и не обходить ограничения личного входа. Применимость дополнительных соглашений проверять по рынку/типу данных: [OpenAI Services Agreement](https://openai.com/policies/services-agreement/), [PHI/BAA guidance](https://help.openai.com/en/articles/8660679-getting-a-business-associate-agreement-for-the-openai-api).

Обязательны per-user quotas, справедливая очередь, отмена/таймауты, отчёт стоимости/лимитов, ресурсная изоляция и overload shedding. Одна тяжёлая история/фотография не задерживает всех пользователей. Общая модель не означает общий медицинский чат. Durable storage и разрешённое компактное окно контекста отделены от session/thread provider.

Ночной разбор выполняется по timezone каждого пользователя, с привязанными owner/device/cutoff/consent и подтверждённым coverage. Советы кэшируются и датируются. Нельзя выдавать отсутствие загруженных данных за отсутствие болезни/гипо/еды или автоматически исполнять советы по ISF/CR/DIA. Потеря сети/подписки/аккаунта не выключает локальную AAPS.

## 8. Релизные допуски

| Gate | Доказательство | Пока не закрыт |
|---|---|---|
| G1 Intended use/markets | Ответственный, scope, review применимых требований | Нет публичного клинического обещания |
| G2 Rights/source | SBOM, JNI rights, notices, source/build воспроизводимость | Нет распространения спорных компонентов |
| G3 Device matrix | Аппаратные записи/known limitations для версии | Нет наследования поддержки «по бренду» |
| G4 Local safety | Differential loop/target/alarms/lifecycle/миграции | Нет автоматического нового control path |
| G5 Privacy/AI | Tenant negative tests, consent, provider/data agreements | Облако недоступно публичным пользователям |
| G6 UX | AAPS Overview unchanged, штатные действия доступны, usability evidence | Нет UI, скрывающего управление/предупреждения |
| G7 Release/recovery | Production signing, update/migration tests, rollout/incident plan | Нет stable channel |

Согласие тестировщика не заменяет все эти доказательства. Закрытое тестирование других пользователей тоже требует подходящих условий и risk review, а не только метки beta.

## 9. Дополнительные потоки реализации

- [ ] Product/regulatory owner: intended use, рынки, release claims, риск/инциденты, правила тестирования.
- [ ] QA/device lab: versioned matrix, тестовые устройства, повторяемые CGM/pump/lifecycle сценарии, реальные подтверждения.
- [ ] Security/privacy: account/device grants, negative isolation tests, ключи, экспорт/удаление, аудит.
- [ ] Release engineer: собственная подпись/applicationId, build provenance, SBOM/JNI/source notices, каналы и recovery.
- [ ] AI/backend: public provider contract, per-user очереди/лимиты/ретеншн и context boundaries, без изменения текущего личного контура.
- [ ] UI integrator: только дополнительные Copilot routes/tabs и их проверки; AAPS Overview/therapy controls не переписываются.

Это дополнения к пяти техническим потокам мастер-плана. Общие contracts/host navigation/Gradle по-прежнему имеют одного интегратора. Ни один из этих пунктов не считается уже выполненным.

## 10. Следующее архитектурное решение

Техническая основа AAPS-host остаётся подходящей и лучше соответствует сохранению интерфейса AAPS. Первый vertical slice: штатный AAPS Overview + три дополнительные страницы Copilot на synthetic facts; virtual pump и fake sensor не открывают реальные соединения.

До реализации уточняются intended use/рынки и первая support matrix. Оценка сроков личной alpha из прежнего варианта не используется как обещание срока публичного продукта. План публичного выпуска не меняет уже установленный Copilot, существующий серверный вход или реальные настройки терапии.
